# 07 — 增量迁移 vs 从头重写：开发思路判定

> 结论：**以迁移为主（约八成沿用），关键单点上"局部重写"。
> 不做整体从零重写。**

## 1. 为什么不全从零写

两个旧项目各已运行多学期，沉淀了大量**只能从真实使用中得到的细节**：

- 2601 动的浏览器代码：学习通登录态保持、课程/作业导航、iframe 层级
  （v1）、直达批阅（v2）、惩罚作业+预扫描（v3）——每一代上传策略都对应
  真实故障场景；重写等于把踩过的坑重新踩一遍；
- 2603 动的排版代码：A4 版式边距/题图缩放/水印位置，经 5–6 学期打印
  验证，看似简单实则调参成本很高；
- 分层标签语义（copy/copySp/copyOnly/qa/summary/distinguish/innovation/
  translation）及其在评阅规则、点名册、学生分组间的联动，是教学经验
  而非代码结构。

## 2. 为什么也不"原样直接搬"

纯代码搬运同样有问题：
- 两边各自演化出了重复/过时的实现（2601 的 uploader 与 submit_v1/v2/v3
  并存、2603 的 wizard 与 webui 双轨），直接搬会把技术债一起搬来；
- 数据契约要变（任务包统一、kb xlsx 为主 05-D3），必须动中带立；
- Python 环境与依赖管理两项目不统一（要收敛到 uv + 一个 pyproject）。

## 3. 判定准则（迁移/重写/新建，逐模块）

| 新模块 | 处置 | 理由 |
|---|---|---|
| xuexitong（登录/浏览/下载） | **迁移**，接口重构 | 浏览器自动化细节昂贵，移植改壳 |
| 上传（v1/v2/v3） | **合并迁移**，择优+保留兜底 | 保留真实故障应对经验 |
| grading（转录/评阅/报告） | **迁移**，prompt 层重写 | prompt 升级为绑定题目+solution |
| kb（xlsx 读写） | **局部重写** | 数据契约升级（快照/同步/schema） |
| 排版（reportlab 竖版） | **迁移改造** | 基线还原 + 新增横版 frame |
| student/roster（分组） | **迁移** | 评分/标签逻辑成熟 |
| wizard/webui 前端 | **废弃，新写 Vue3** | 前端是两种范式，勉强移植不如按 D4/D13 重做（新写成本低于改造） |
| CLI（两个 cli.py） | **合并重构** | 命令组统一 `assist`，click 复用 |
| 水印/latex 样题图 | 迁移 | 工具型、已稳定 |

## 4. 配套纪律（防"轮子"）

- 迁移前先读旧实现（_legacy/ 即参考库），能用则**函数级搬运并注明来源
  （注明来自 _legacy/2601 或 2603 的哪个文件）**；
- 依赖库不上自研重复轮：xlsx 用 openpyxl、HTTP 用 httpx、
  配置校验用 pydantic——除非标准库/现有依赖已覆盖；
- 新写代码给出 README/文档级理由（在 PR/commit 描述中一句即可），避免
  "顺手重新实现"。

## 5. 验收检查点（每阶段结束时自问，防止形同虚设）

每次阶段完成验收时问一句：
1. 本阶段哪些代码从 _legacy 迁入（清单）？哪些新写、为何？
2. 旧行为是否有"悄悄改变"而无迁移记录？
3. 阶段代码是否可通过 CLI 复现（D1 铁律校验）？
