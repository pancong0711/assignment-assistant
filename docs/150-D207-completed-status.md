# D207：真实平台状态是「Completed（教师提交）」——修正状态解析与核验口径

> 日期：2026-11-19
> 状态：**已完成（2026-11-19）**
> 关联：`docs/149-D206-real-platform-validation.md`
>
> 隐私：不记录学生姓名/批语正文。

---

## 0. 问题

D206 实测时，核验结果里 `status` 是**空串**，只能靠“分数一致”兜底判定成功。
这留下一个真实风险：

> 平台在**只改分、未点提交**时也可能把分数保存下来（D206 首次失败尝试中，
> 列表已显示 88 分），因此“分数一致”**不能证明批阅已提交**。

## 1. 真实原因

真实批阅列表行文本为：

```text
<学生名> <学号> Completed（教师提交） 11-19 22:09 View return
```

状态字段是 **`Completed（教师提交）`**，既不是“已批阅”也不是 `Reviewed`。
旧解析只匹配 `待批阅|已批阅|补交|未交|Reviewed|Unreview`，因此读成空串。

## 2. 修复

### R1. 列表状态解析

`extractor.JS_REVIEW` 增加 `Completed | 完成 | 教师提交`。

### R2. 核验口径（防假成功）

```python
pending  = 状态匹配 待批阅|unreview|未完成|unsubmitted
reviewed = not pending 且 状态匹配 已批阅|补交|reviewed|completed|完成|教师提交
```

判定顺序：

1. 状态**明确**未批阅 → 失败（即使分数一致也失败）；
2. 分数与期望不一致 → 失败；
3. 状态为空但分数一致 → 通过并记 `note`（兼容极端情况）；
4. 其余 → 失败。

## 3. 真实平台复验结果

| 检查 | 结果 |
|---|---|
| 列表状态解析 | `Completed（教师提交）` ✅ |
| 正向核验（期望 100） | `ok=true`，`status=Completed（教师提交）`，`note=null`（不再靠分数兜底） |
| 负向核验（期望 77） | `ok=false`，`提交后平台分数为「100」，与期望 77 不一致` ✅ |

平台最终状态：分数 `100`、批语 233 字、2 张图（已还原，未改动批语）。

## 4. 测试

新增 `engine/tests/test_d207_completed_status.py`（6 项）：

- `Completed（教师提交）` / `Completed` → 视为已批阅；
- `Completed` 但分数不符 → 失败；
- `Unreview` + 分数一致 → **仍失败**（防“只改分未提交”假成功）；
- `待批阅` + 分数一致 → 失败；
- 源码契约。

全量 pytest：`1883 passed`。

## 5. 仍然存在的边界（诚实说明）

- `Completed（教师提交）` 的判定依赖列表行文本；若平台再改文案，需要同步更新关键词；
- 若某版本平台**既不渲染状态文本、也无法读到分数**，核验只能报“无法确认已保存”；
- 真实平台的 UEditor 细节仍可能变化（本次实测插图成功）。

建议：每次平台改版后，用「演练 + 上传」各测 1 名学生，并检查
`upload/<workId>.json` 的 `afterSubmit.status` 是否为 `Completed…`。
